### Opposing Agent 3 - Architecture/Security Skeptic

#### Scope and call-graph evidence

The worker-to-Tk path is `AppCoordinator.worker()` (`src/expra_engine/coordinators/app_coordinator.py:188-205`) -> injected `deliver` -> `TkDeliveryQueue.__call__()` (`src/expra_engine/editor/delivery.py:44-49`) -> `Queue.put()` -> Tk-scheduled `_drain()` (`delivery.py:82-109`) -> the application callback. The editor composition root wires this queue into `AppCoordinator` at `src/expra_engine/ui/editor_window.py:123-127`.

The supported shutdown path is `RuntimePreviewLoop.stop()` -> `TimerDelivery.cancel_all()` -> `ContributionRegistry.stop_all()` -> `TkDeliveryQueue.close()` -> `AppCoordinator.shutdown()` -> `UICoordinator.shutdown()` -> `root.destroy()` (`editor_window.py:898-922`). The repository contract is explicit that workers may only use the delivery entry point and may not call any Tk API (`docs/ARCHITECTURE.md:75-103`, `docs/THREADING.md:3-7`).

#### Worker/Tk boundary, lock ordering, and reentrancy

- **Severity: none for the supported call graph. Verdict: no patch regression found.** `__call__()` takes `_state_lock` across only the closed-state check and the unbounded `Queue.put()` (`delivery.py:44-49`). `_drain()` clears the timer state under the lock, releases it before invoking application callbacks, and reacquires it only for the final closed check and `after(25, ...)` (`delivery.py:82-107`). `_close()` uses the same state-lock -> queue-operation order (`delivery.py:68-80`); no path found acquires the queue mutex and then `_state_lock`. The `RLock` permits a same-thread callback or fake Tk adapter to re-enter `close()` without deadlock.
- The exact focused queue tests passed: `tests/test_delivery_queue.py` was included in `98 passed, 2 subtests passed`; the focused coordinator/timer command passed `90 passed`. A reentrant probe produced `markers=['before-close', 'after-close-call'], closed=True, pending_after_close=0`; a display-backed worker probe under `xvfb-run` delivered `400` of `400` unique callbacks, with `errors=[]`, every callback on the Tk main thread, and `closed=True`.
- Close is linearizable for callbacks still in the queue: a callback is either accepted before close and drained/discarded, or rejected after the closed bit is set. A callback already removed by `_drain()` may finish after a concurrent `close()`; that is consistent with the public contract, which promises to stop accepting and discard pending callbacks, not to interrupt an in-progress callback. No duplicated callback was observed.
- **Severity: P2 hardening concern, not a confirmed current-integration bug. Verdict: unsupported worker-thread `close()` remains unsafe.** `_close()` holds `_state_lock` while calling Tk `after_cancel()` (`delivery.py:68-75`). The current callers (`EditorWindow._on_close()` and the `<Destroy>` callback) are on the Tk thread, while worker code uses only `__call__()`. If a caller invokes public `close()` from a worker, Tk's cross-thread marshaling can wait for the Tk thread while a drain needs `_state_lock`, creating a possible lock/Tk wait cycle. The patch did not add a worker `close()` call site, so this is an API hardening issue rather than a patch-introduced failure under repository usage.

#### Close/drain behavior, root destruction, and callback isolation

- **Severity: none for the queue's fail-closed contract. Verdict: control is sufficient for the tested paths.** Constructor binding/scheduling failure closes the queue (`delivery.py:35-38`); a missing or destroyed widget closes it without rescheduling (`delivery.py:87-93`); reschedule failure calls `_close()` and discards callbacks queued during that failure (`delivery.py:103-109`). The display-backed probe and the focused constructor/reschedule/destroy tests exercised these transitions. Late worker completions therefore cannot call Tk after the queue is closed.
- **Severity: none for ordinary application callback failures. Verdict: no patch issue found.** `_drain()` catches `Exception` per callback (`delivery.py:94-102`), then continues to later callbacks and the periodic reschedule. The focused callback probe produced `later=['later']` and `closed=False` after an earlier callback raised `RuntimeError`. `AppCoordinator` separately isolates result, progress, subscriber, and finalizer callbacks (`app_coordinator.py:227-231,274-312`). `BaseException` is intentionally not swallowed; treating `KeyboardInterrupt`/`SystemExit` as ordinary application failures would be unsafe and was not promoted to a defect.
- **Severity: P2. Verdict: confirmed patch-introduced fail-open state on live-root scheduling failure.** `_act_play()` changes the engine to `PLAY` before calling `RuntimePreviewLoop.start()` (`editor_window.py:445-450`). The amended `start()` now catches `RuntimeError`/`tk.TclError`, stores no timer, and returns without stopping the engine, logging, or exposing an error (`runtime_preview.py:22-29`). A deterministic probe with `winfo_exists() == True` and `after()` raising `tk.TclError('event loop unavailable')` produced `{'state': 'PLAY', 'timer': None}`. This is distinct from an actually destroyed root, for which the new existence guard correctly produced `timer=None`. The patch therefore hides a live scheduling failure while leaving runtime state claiming PLAY and with no future tick; it is a reliability/observability defect, not a security or privilege-boundary issue.
- **Severity: P2. Verdict: pre-existing root/engine lifecycle gap, not introduced by this diff.** On external root destruction, `_root_exists()` makes the preview timer fail closed, but neither `RuntimePreviewLoop` nor `EditorWindow._on_close()` calls `Engine.stop()`. The engine can remain in `PLAY`, with runtime systems/behaviours not receiving their normal stop teardown, after the Tk root is gone. The amended liveness check improves avoidance of stale Tk calls but does not settle engine state; the editor close ordering and missing engine stop predate this patch.

#### Coordinator shutdown and dropped completions

- **Severity: P1. Verdict: confirmed pre-existing lifecycle bug, not patch-introduced.** `EditorWindow._on_close()` closes delivery before `AppCoordinator.shutdown()` (`editor_window.py:917-920`). `AppCoordinator.shutdown()` uses `ThreadPoolExecutor.shutdown(wait=False, cancel_futures=True)` but does not `cancel_all()` or wait for already-running tasks (`app_coordinator.py:337-372`). A running worker can therefore call `deliver()` after queue close; the callback is correctly dropped to protect destroyed Tk, but `_complete_run()` never settles `in_flight`, clears callbacks, invokes `on_finished`, or processes a rerun. The exact current-tree probe produced `queued_before_close: {'queue_closed': True, 'in_flight_before_shutdown': True}` and `shutdown_after_drop: {'in_flight': True, 'has_pending_work': True}`. This is the correct fail-closed UI behavior paired with an incomplete coordinator lifecycle; neither the editor close ordering nor coordinator shutdown changed in this patch.

#### Shortcut registration atomicity, routing, and cleanup

- **Severity: none for in-memory feature registration. Verdict: the amended duplicate check is effective for the tested Tk aliases.** `ContributionRegistry.register()` computes all normalized sequences and rejects intra-feature duplicates before mutating `ButtonCoordinator` or `ShortcutRegistry` (`contributions.py:132-178`). Current probes rejected all three pairs with `ValueError: Feature contains duplicate shortcuts: alias-probe`: `<Control-Key-e>`/`<Control-KeyPress-e>`, `e`/`<KeyPress-e>`, and `<Control KeyPress e>`/`<Control-e>`. The focused contribution tests passed as part of `98 passed, 2 subtests passed`. Cross-feature validation also occurs before action mutation. No duplicate or partial in-memory registration was reproduced.
- **Severity: P2. Verdict: confirmed patch-introduced shortcut grammar regression.** The new `elif len(value) == 1 and value.isprintable()` branch wraps every printable character in angle brackets (`contributions.py:272-284`), but Tk accepts simple printable patterns such as `+`, `>`, `[`, and `-` without angle brackets and rejects `<+>`, `<>>`, `<[>`, and `<->`. The same probe showed `é` and `中` become `<é>`/`<中>` and fail at `root.bind_all()`. The amended normalizer also splits the whole interior of a string that starts and ends with angle brackets, so valid multi-event `<Control-z> <Control-x>` becomes `<Control-z>-<Control-x>`; Tk accepts the rewritten binding command but it no longer denotes the original two-event sequence. `<Key>` and `<Control-Key>` are also newly reduced to `<>` and `<Control>`, which fail binding, whereas the pre-change normalizer preserved the `Key` event type. This is a public API/platform regression beyond the tested alphabetic aliases and can cause registration to succeed but editor construction or feature binding to fail later with `tk.TclError`.
- Exact display-backed output was: `'+': '<+>' -> TclError: bad event type or keysym "+"`; `'>': '<>>' -> TclError`; `'[': '<[>' -> TclError`; `'-': '<->' -> TclError`; `'é': '<é>' -> TclError`; `'中': '<中>' -> TclError`; `'<Key>': '<>' -> TclError`; `'<Control-Key>': '<Control>' -> TclError`; and `'<Control-z> <Control-x>': '<Control-z>-<Control-x>' -> bound`. Plain `e` still bound as `<e>`, so this is an edge-case grammar regression, not a universal shortcut failure.
- **Severity: P2. Verdict: confirmed pre-existing live-root binding cleanup gap, not introduced by this diff.** `ShortcutRegistry.bind()` installs anonymous `root.bind_all()` handlers (`contributions.py:264-269`), while `ContributionRegistry.unregister()` removes only the registry mapping and action (`contributions.py:224-229`); it has no corresponding `unbind_all`. A fake-root lifecycle probe registered/bound `<Control-z>`, unregistered it, registered a replacement, and bound again; invoking the two retained handlers produced `bindings=2, calls=['second', 'second']`. This is a user-visible duplicate action route for dynamic feature unregister/re-register on a live root. The built-in editor binds once and destroys the root, so the current static path does not trigger it, but the public registry lifecycle contract does.
- **Severity: P2. Verdict: confirmed pre-existing Tk binding atomicity gap, not introduced by this diff.** `ShortcutRegistry.bind()` has no rollback if `bind_all()` fails midway. A fake root that raised `tk.TclError` on the second bind produced `bind_calls=['<Control-a>', '<Control-b>']` and left both registry sequences installed, with the first Tk binding already present. Thus in-memory registration is transactional, but binding the public surface is not. This is relevant to platform/Tk shutdown or binding failures, but no security boundary or privilege escalation was found.
- User-visible shortcut dispatch still routes through `ButtonCoordinator.dispatch()` and therefore respects disabled actions (`contributions.py:260-269`, `button_coordinator.py:91-111`). No new security issue, arbitrary worker-to-Tk route, or cross-user data exposure was found in shortcut canonicalization. The remaining risks are lifecycle and UI routing reliability.

#### Overall Agent 3 verdict

The queue lock/close changes are supported by focused tests and real-Tk concurrency evidence, and the amended alias normalization closes the previously reproduced duplicate-registration forms for the tested alphabetic aliases. The patch is **not safe to sign off without qualification** because live-root `after()` failure is now silently fail-open with engine state stuck in `PLAY`, and the new shortcut normalizer rejects valid punctuation/event-pattern forms (both confirmed P2, patch-introduced). The P1 coordinator settlement issue, root/engine teardown gap, worker-thread `close()` hazard, and Tk binding cleanup/rollback gaps are separately identified as pre-existing or unsupported-call-path concerns and should not be misattributed to the amended queue/normalizer change. No production code or tests were changed during this review.

### Opposing Agent 4 - External-Research Skeptic

**Verdict: not safe as amended.** The Tk delivery and runtime-root changes are
supported by the documented semantics and local probes, but
`ShortcutRegistry.normalize` has confirmed patch-introduced semantic regressions
for valid Tk patterns. These are P2 correctness findings because ordinary
single-key alphabetic shortcuts still work, while valid edge-case declarations
can later fail during `bind_all` or silently stop matching.

#### Authoritative sources

- Tcl/Tk 8.6 `bind`: https://www.tcl-lang.org/man/tcl8.6/TkCmd/bind.htm
  states that event fields may be separated by whitespace or dashes; `KeyPress`
  and `Key` are synonyms; a type may be omitted only when a detail is present;
  a simple pattern is one printing ASCII character (excluding space and `<>`
  handling as specified); and a sequence may contain multiple event patterns
  with optional whitespace between them. It lists `Control` and `Alt`, but does
  not list `Ctrl` as an alias.
- Tcl/Tk 8.6 `after`: https://www.tcl-lang.org/man/tcl8.6/TclCmd/after.htm
  says timer callbacks run once through the event loop, return an identifier,
  and `after cancel` is a no-op for an already executed/canceled identifier.
- Tcl/Tk 8.6 `winfo`: https://www.tcl-lang.org/man/tcl8.6/TkCmd/winfo.htm
  defines `winfo exists` as 1 for an existing window and 0 otherwise.
- Python 3.12 `tkinter`: https://docs.python.org/3.12/library/tkinter.html
  documents that foreign-thread calls may be posted to the interpreter event
  queue when the event loop is running, but fail when it is not.
- Python 3.12 `queue`: https://docs.python.org/3.12/library/queue.html
  documents `Queue` as synchronized for multi-producer/multi-consumer use and
  explicitly says the queue classes are not reentrant within one thread.
- Python 3.12 `threading.RLock`:
  https://docs.python.org/3.12/library/threading.html#rlock-objects
  documents same-thread recursive acquisition and paired release semantics.
- CPython 3.12 Tkinter implementation:
  https://github.com/python/cpython/blob/3.12/Lib/tkinter/__init__.py
  shows `CallWrapper.__call__` routes ordinary callback exceptions to
  `report_callback_exception`, while `SystemExit` is re-raised.

#### Local probes and results

- Environment: `python3 -VV` reported Python 3.12.3; `_tkinter` and Tk/Tcl
  reported 8.6, and a Tcl interpreter reported patchlevel 8.6.14.
- `PYTHONPATH=src python3 -m pytest -q tests/test_editor_contributions.py tests/test_delivery_queue.py tests/test_editor_ui.py`:
  `61 passed, 2 subtests passed`. This validates the repository fakes and
  amended regression tests, but is not proof of all native Tk patterns.
- `PYTHONPATH=src python3` normalizer probe:
  `<Control-KeyPress-z>`, `<Control-Key-z>`, `<Control z>`, and
  `<Control KeyPress z>` all normalize to `<Control-z>`; `e`, `<e>`, and
  `<KeyPress-e>` normalize to `<e>`. These are safe and matched in a native Tk
  dispatch probe.
- `PYTHONPATH=src xvfb-run -a python3` native `bind` probe on Tk 8.6.14:
  `<Control-KeyPress-z>`, `<Control-Key-z>`, `<Control z>`,
  `<Control KeyPress z>`, `<KeyPress>`, and `<Key>` were accepted;
  `<ctrl-z>`, `<CONTROL-z>`, `<é>`, and `<中>` were rejected. Plain `e`, `>`,
  `[`, and `-` were accepted as simple patterns.
- The same native probe after normalization produced:
  `<KeyPress>` -> `<>`, `<Key>` -> `<>`, `<Control-KeyPress>` ->
  `<Control>`, `<Control-Key>` -> `<Control>`, `>` -> `<>>`, `[` -> `<[>`,
  `-` -> `<->`, `é` -> `<é>`, and `中` -> `<中>`. Tk rejected every one of
  those normalized forms. This is a direct proof that `isprintable()` is
  broader than Tk's printing-ASCII form and that omission is unsafe without a
  detail field.
- Native two-event probe: Tk accepted `<Control-z> <Control-x>` and
  `<Control-z><Control-x>`. The amended normalizer changed the first to
  `<Control-z>-<Control-x>`. Binding both and generating Control-z followed by
  Control-x dispatched only the original binding, proving the rewrite is not
  equivalent. The older split-on-dash implementation did not introduce this
  whitespace-crossing regression.
- Tcl `after` probe: `after 0` returned `after#0`, `after info` listed it,
  `after cancel` prevented execution, and `update` executed an uncanceled
  timer. A timer queued before `root.destroy()` did not run; Tkinter
  `after_cancel` after destruction returned without error. A destroyed child
  returned `winfo_exists() == 0`; after destroying the entire application,
  `root.winfo_exists()` raised `TclError` because the application itself was
  gone. This last case is not specified as a normal 0 result by the man page,
  but is correctly covered by the amended `TclError` catch.
- Thread probe: a foreign `root.winfo_exists()` call without a running
  mainloop raised `RuntimeError: main thread is not in main loop`; the same
  call while `mainloop()` was active returned `('ok', 1)`. Therefore Tkinter
  can marshal some calls, but the queue's worker path is safer because
  `TkDeliveryQueue.__call__` touches only `Queue` and `RLock`, never Tk.
- Queue/RLock probe: FIFO `Queue.get_nowait()` returned the inserted item and
  then `Empty`; nested `RLock` acquisition succeeded and the lock remained
  held until the matching releases. The queue close-race test passed, and a
  callback queued after close was not delivered. No queue/RLock regression was
  proven.
- Callback probe: a native `root.after` callback raising `ValueError` reached
  the overridden `report_callback_exception`; a queued callback raising
  `ValueError` was suppressed and the later queued callback plus rescheduling
  still ran. `contextlib.suppress(Exception)` did not suppress
  `KeyboardInterrupt` or `SystemExit`. The queue behavior is an observability
  difference from native Tk callbacks, but the suppression was unchanged by
  this patch, so it is not a patch-introduced finding.
- Runtime probe: a fake root without `winfo_exists` scheduled normally; a fake
  root returning true scheduled normally; false or `TclError` from
  `winfo_exists` prevented scheduling. Play ticked, rendered, and rescheduled;
  Paused rescheduled without ticking; Edit did not reschedule. This supports
  fail-closed checks without breaking valid fake roots or normal scheduling.

#### Findings

- **A4-1, confirmed patch-introduced:** `contributions.py:277-281` removes
  `Key`/`KeyPress` even when there is no detail. Tk permits `<KeyPress>`,
  `<Key>`, `<Control-KeyPress>`, and `<Control-Key>` as type-only patterns,
  but normalization converts them to `<>` or `<Control>`, which native Tk
  rejects. The added `Key` omission broadens the prior defect; the whitespace
  parser also exposes it for valid separator forms.
- **A4-2, confirmed patch-introduced:** `contributions.py:277` parses the
  entire angle-bracketed string as one event pattern. A valid multi-event
  sequence containing optional whitespace is rewritten with a literal hyphen
  between patterns and no longer matches. This violates the official `bind`
  sequence grammar and was reproduced with native event generation.
- **A4-3, confirmed patch-introduced:** `contributions.py:282-283` wraps every
  one-character `str.isprintable()` value. Tk's simple form is restricted to
  printing ASCII and already accepts legal punctuation directly; the amended
  wrapper turns `>`, `[`, and `-` into rejected long forms and turns printable
  non-ASCII characters into rejected Tk keysyms on this supported Tk build.
  `e` remains safe, but the branch is not generally semantics-preserving.
- **A4-4, research limitation / not a separate confirmed bug:** the official
  man page does not specify post-application-destruction behavior for every
  Tkinter method, and the local Tk 8.6.14 result (`TclError` from root
  `winfo_exists`) cannot establish behavior across every supported Tcl/Tk
  build. The amended catches cover the documented `RuntimeError`/`TclError`
  failure boundary and the valid fake-root behavior was directly tested.

#### Final Agent 4 decision

The delivery queue synchronization, timer cancellation handling, callback
continuation policy, Tk thread boundary, and RuntimePreviewLoop root checks
are externally consistent and locally supported. The shortcut normalizer is
not externally safe as amended: A4-1 through A4-3 are reproducible semantic
regressions. Before accepting the patch, preserve multi-pattern sequences and
only omit `Key`/`KeyPress` when a detail is present; printable canonicalization
must be restricted to forms proven equivalent by Tk rather than Python's broad
`isprintable()` predicate.
