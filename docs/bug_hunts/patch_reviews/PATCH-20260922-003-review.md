#### Boundary and threat-model trace

The intended data flow is:

`Scene JSON -> component_from_dict() -> Entity components -> render_extractor ->`
`neutral RenderFrame.submissions -> RenderPlanBuilder -> PygameScreenPipeline`.

The neutral request and marker types in
`src/expra_engine/runtime/screen_texture.py:339-427` carry IDs, transforms,
sampling values, and immutable value objects only. They do not carry a surface,
operation, or Pygame object. `Scene.to_dict()` serializes component dictionaries
only, while `PygameScreenPipeline._captures` is created after extraction and is
owned by the renderer adapter. This boundary is sound for the normal scene path.

The separate legacy edge is `project_runner.frame_factory()` creating one
neutral frame with both `submissions` and a `PygameRenderFrame` payload. That
payload enters `PygameRenderer.render()` after the canonical plan, which is the
source of the first finding below.

#### Confirmed finding 3: renderer capabilities overclaim partial backends (P2)

`pygame_renderer.py:158-177` reports `screen_capture` when a target exposes only
`subsurface()` and `copy()`, but `_clip_rect_to_surface()` at
`pygame_screen_pipeline.py:414-423` also requires `get_size()`. It reports
`screen_texture` when either `scale()` or `smoothscale()` exists, while the
default `ScreenTextureFilter.LINEAR` path calls `smoothscale()` at
`pygame_screen_pipeline.py:335-352`. The capability contract therefore cannot
be used to gate the operations that the frame will actually request.

Counter-tests:

- A surface with `subsurface()` and `copy()` but no `get_size()` printed
  `capture capability without get_size True`, then raised
  `UnsupportedScreenPipelineFeature: Pygame target surface does not expose
  get_size()` during a capture.
- A surface with `subsurface()`, `copy()`, `blit()`, and only `transform.scale()`
  printed `capability True True False`, then raised
  `UnsupportedScreenPipelineFeature: Pygame backend cannot scale screen textures`
  for the default linear consumer. The same partial backend completed a
  nearest-filter consumer, proving the flag is too coarse/optimistic rather
  than the whole pipeline being unreachable.

This is P2 because a caller trusting the advertised capability can enter an
unhandled runtime error on an otherwise accepted backend. The detector needs to
cover all required operations or expose capability granularity sufficient for
filter, crop, rotation, and capture requirements; explicit backend errors
should remain fail-loud rather than being advertised as supported.

#### Confirmed finding 4: malformed serialized flags are coerced into active effects (P2)

The new deserializers use `bool(data.get(...))` for `enabled` and `visible` at
`screen_texture.py:224-232` and `321-335`. A non-empty string such as JSON
`"false"` becomes `True`. `_capture_id()` also stringifies `None`, so a null
capture ID becomes the valid slot name `"None"` instead of being rejected. This
crosses the persisted-scene trust boundary and can activate a capture/consumer
that serialized data attempted to disable.

The direct `capture_id: None` probe produced `capture_id 'None'` for both

meaning. Severity is P2: this is a correctness and effect-activation boundary,
not an arbitrary code-execution path.

post-review implementation and regression evidence address each one:
